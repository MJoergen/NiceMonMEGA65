# Surveying BASIC dialects to shape a NICE ROM interpreter

A survey made on 2026-10-31 for [#54](https://github.com/MJoergen/NiceMonMEGA65/issues/54), a BASIC interpreter in the ROM. The PDF of it is attached to that issue.

BASIC has split into four lineages that matter for a ROM interpreter on the NICE CPU. The first is the Microsoft family: single-byte keyword tokens, text left in place, a linked list of numbered lines, and a 40-bit software float. Commodore BASIC V2 sits here, and so does BASIC 65 on the MEGA65, which is "an enhanced version of BASIC 10" and keeps line numbers, the screen editor, 5-byte reals and two-significant-character names ([MEGA65 BASIC 65 Reference](https://files.commodore.software/reference-material/manuals/commodore-64-manuals/hardware-manuals/mega65-basic65-reference-may-2022.pdf)). The second is the non-Microsoft 8-bit group (Apple Integer BASIC, Atari BASIC, Sinclair, BBC BASIC, Locomotive, TI), whose main lessons are about speed and editing. The third is the structured and standardized line: Dartmouth, ECMA-55 Minimal BASIC, ANSI Full BASIC, QuickBASIC, True BASIC. The fourth is today's small interpreters: MMBasic, uBASIC, my_basic, Bas, bas55, EndBASIC and others. The evidence says the speed differences between dialects come mostly from a few implementation choices, not from the language: how GOTO finds its line, how NEXT finds its FOR, whether integers have a fast path, and how strings are collected. All four are cheap to get right on a 32-bit word machine with hardware multiply and divide. The best-supported shape for the target is a BBC-style integers-first interpreter with optional line numbers and a screen-reading editor, with the sizing and float questions flagged below because the notes did not settle them. The notes have real gaps (BASIC 65 ROM size, soft-float costs on a comparable CPU, most structured-dialect syntax), and each is marked where it matters.

## Microsoft lineage: one core, a 40-bit float, and slow late-binding

All Microsoft descendants share single-byte keyword tokens, `$ % # !` type suffixes, and DATA/READ-style statements. The 6502 versions use a 40-bit float (4-byte mantissa, 1-byte exponent) that "became the most common" on 6502 machines, and only the first two characters of a variable name count ([Wikipedia: Microsoft BASIC](https://en.wikipedia.org/wiki/Microsoft_BASIC)). The 6502 interpreter fits in **just under 8 KB** with single precision and **9 KB** with the 40-bit float (same source). Microsoft's own source shows how little it does at entry: each line is a link pointer, a 2-byte line number, the text with keywords tokenized, and a zero byte ([microsoft/BASIC-M6502](https://github.com/microsoft/BASIC-M6502/blob/main/m6502.asm)). The 9-digit float library is a little over 2 KB of that ([pagetable.com](https://www.pagetable.com/?p=46)).

Run-time costs follow from this design. A simple variable is a 6-byte entry found by linear search (2 name bytes, 4 value bytes). GOTO starts from the program start only when the target is not above the current line; otherwise it walks forward from the current line (m6502.asm, above). A FOR frame on the stack is 18 bytes in the 40-bit build and a GOSUB frame 5 bytes. NEXT searches the stack for its FOR frame, not the program (same source). Expression evaluation is a precedence-climbing routine that uses the machine stack as its operator stack, and it checks stack room at each level, so deep nesting gives "?OUT OF MEMORY" ([mist64/msbasic eval.s](https://raw.githubusercontent.com/mist64/msbasic/master/eval.s)). Strings are 3-byte descriptors (length plus a 16-bit pointer). C64 V2 garbage collection rescans all descriptors repeatedly and costs about N-squared in the number of heap strings: hundreds of strings can freeze the machine for 20 minutes, and a 9000-element test took about 1 h 49 min versus 3.4 s for a replacement routine ([C64-Wiki: Garbage Collection](https://c64-wiki.com/wiki/Garbage_Collection)). BASIC 4.0, 3.5 and 7.0 fixed this with a 2-byte back pointer per heap string so one sweep removes all gaps (same source). The temporary-string stack has only three slots, which is the real source of "FORMULA TOO COMPLEX" (msbasic string.s; the notes mark the exact slot count as unverified for the C64).

BASIC 65 keeps this core but changes the numeric picture. It adds `%` 16-bit integers and `&` byte variables beside reals, and variables take 8 bytes each. One-letter variables are "fast variables" at fixed addresses in `$FD00-$FEFF`; two-letter names need a table search (BASIC 65 Reference, above). Arrays use item sizes of 1, 2, 5 and 3 bytes for byte, integer, real and string descriptors, and program text (bank 0) is separate from variables, arrays and strings (bank 1, about 55,000 bytes). The reference never states the float format; the 5-byte item size points to the Microsoft 40-bit format. A ROM-repository issue says BASIC 65 "uses MEGA65 hardware math registers for division" and a commenter says it feeds normalized mantissas to the divider, which lost precision until a fix in August 2024 ([mega65-rom-public issue 101](https://github.com/MEGA65/mega65-rom-public/issues/101)). Whether it also uses the hardware multiplier is not documented in anything the notes read. The notes found no BASIC 65 versus V2 speed comparison and no ROM size for BASIC 65.

The Commodore line is mostly a story of accumulating commands. The notes' table traces it as V2 baseline; 3.5 (sound, graphics, DO/LOOP/WHILE/UNTIL/EXIT, AUTO/DELETE/RENUMBER, TRON/TROFF, MONITOR); 4.0 (disk commands, fast garbage collection); 7.0 (sprites, BEGIN/BEND, WINDOW, banking, FAST/SLOW); 10 (PALETTE, MOUSE, FIND/CHANGE, DMA); and 65 ([Wikipedia: Commodore BASIC](https://en.wikipedia.org/wiki/Commodore_BASIC)). BASIC 65's structured set is exactly the 7.0 one: `DO [UNTIL|WHILE] ... EXIT ... LOOP`, `BEGIN...BEND` (needed only because IF is single-line), `TRAP`/`RESUME`/`ER`/`EL`/`ERR$`, and `ON expr GOTO/GOSUB`. It has no ON KEY or ON TIMER, only `COLLISION`. Its editing commands are AUTO, RENUMBER with ranges, DELETE ranges, `LIST P` paging, HELP, and FIND/CHANGE where a `/` delimiter searches tokenized keywords and a `"` delimiter searches literal text. Its operators add `<<`, `>>`, and 16-bit AND/OR/XOR/NOT with TRUE = -1 (BASIC 65 Reference). GW-BASIC is the PC-side cousin: 40-character names, `WHILE/WEND`, event traps, and a full-screen editor ([Wikipedia: GW-BASIC](https://en.wikipedia.org/wiki/GW-BASIC)).

## The other 8-bit BASICs show what speed actually costs

The non-Microsoft dialects are useful because each made one different choice and the benchmarks expose the result. Apple Integer BASIC (Wozniak) had **16-bit integers only**, no floating point, and tokenized whole lines including numbers. It was over twice as fast as Applesoft in the Rugg/Feldman tests ([Wikipedia: Integer BASIC](https://en.wikipedia.org/wiki/Integer_BASIC)). Atari BASIC pre-parses at entry into a parse-tree form: keywords become tokens, variable names become one-byte table indexes (so at most 128 variables), and numbers become 6-byte floats. Syntax errors show up at entry as inverse video. It is nonetheless the slowest of the set: GOTO/GOSUB scan the whole program, each NEXT searches the program for its FOR, and BCD-to-integer conversion of line numbers and array indexes takes up to 3,500 microseconds ([Wikipedia: Atari BASIC](https://en.wikipedia.org/wiki/Atari_BASIC)). Turbo-BASIC XL recovered 3-5x just by fixing exactly those points: a hashed line table for GOTO, a stored address in each FOR, and a faster math pack ([Wikipedia: Turbo-BASIC XL](https://en.wikipedia.org/wiki/Turbo-BASIC_XL)). TI BASIC is slow for architectural reasons: it runs as GPL bytecode on the slow side of an 8-bit bus ([Wikipedia: TI BASIC](https://en.wikipedia.org/wiki/TI_BASIC_(TI_99/4A))).

BBC BASIC is the dialect that combined speed and structure. It added `PROC`/`FN` with parameters, `LOCAL`, `REPEAT/UNTIL`, one-line IF/ELSE (and from BASIC V multi-line IF, WHILE, CASE, local arrays and local error handlers), long case-sensitive names, 32-bit `%` integers and an inline assembler, all while staying compatible with Microsoft BASIC at the BBC's insistence ([Wikipedia: BBC BASIC](https://en.wikipedia.org/wiki/BBC_BASIC)). Sophie Wilson said labels were dropped because "the BBC committee insisted on line numbers" ([Wilson interview](https://retroisle.com/others/acornbbc/Articles/sophie_wilson_interview.php)). The 6502 version fit in a 16 KB ROM. Its tokenized line is `0D, line hi, line lo, length, tokens`, with GOTO/GOSUB targets stored as token `0x8D` plus three bytes of binary line number, split so no byte collides with the ELSE token and the skipper can pass over them ([Xania: BBC BASIC V format](https://www.xania.org/200711/bbc-basic-line-number-format)). The notes credit its speed to fixed integer variables A%-Z%, separate integer routines, variable lists split by first letter, and fast shared RAM ([Wikipedia: BBC BASIC](https://en.wikipedia.org/wiki/BBC_BASIC)). Heap strings are allocated in power-of-two classes so no compacting collector is needed ([BB4W manual](https://bbcbasic.co.uk/bbcwin/manual/bbcwind.html)). Later versions move to 32-bit and 64-bit integers; BASIC VI uses IEEE 8-byte reals. Locomotive BASIC added AFTER/EVERY timers and sound queues ([Wikipedia: Locomotive BASIC](https://en.wikipedia.org/wiki/Locomotive_BASIC)).

The benchmark numbers back the conclusion that a leaner interpreter beats a faster clock. On the Byte sieve (seconds, lower is faster) the BBC Master took 76, the BBC Micro B 101, Apple IIe Integer 134, Applesoft 211, the C64 254, and Atari 800XL 316 ([lowendmac](https://lowendmac.com/2016/how-fast-were-those-late-1970s-home-computers/)). On the Rugg/Feldman suite, the BBC Micro (2 MHz) scored 0.8, 3.1, 8.1, 8.7, 9.0, 13.9, 21.1 and 49.9 seconds against the C64's 1.2, 9.3, 17.6, 19.5, 21.0, 29.5, 47.5 and 119.3 ([Wikipedia: Rugg/Feldman](https://en.wikipedia.org/wiki/Rugg/Feldman_benchmarks)). On the Ahl benchmark Atari BASIC took 6 min 58 s against about two minutes for Apple II and C64 ([Wikipedia: Creative Computing Benchmark](https://en.wikipedia.org/wiki/Creative_Computing_Benchmark)). One caution: a second source in the notes gives different Rugg/Feldman test-1 numbers (BBC 0.5, C64 0.8) with unlabeled units, and the Wikipedia sieve figures for Integer BASIC and TI BASIC come from different runs than lowendmac's table, so the scales do not compare across sources. For BASIC 65 itself the only speed evidence is that the MEGA65 runs 6502 code "close to 40x stock C64 speed" ([c65gs blog](https://c65gs.blogspot.com/2018/12/mega-6502-benchmark-for-checking-cycles.html)) and that `SPEED` selects 1, 3.5 or 40 MHz (BASIC 65 Reference).

## Standards and structured dialects describe a design menu

BASIC began at Dartmouth in 1964 with 12 statements, all-float arithmetic of about 30 bits, variable names of a letter or a letter and digit (286 names), and a line-number editing model where a numbered line is stored, a bare number deletes it, and anything else runs immediately ([Wikipedia: Dartmouth BASIC](https://en.wikipedia.org/wiki/Dartmouth_BASIC)). That editing model is still the one a C64 user types. Dartmouth itself did not freeze. It added `SUB...SUBEND` with parameters in 1971, `DO/LOOP`, `SELECT CASE` and block `IF` by 1975-76, recursion by activation records in 1980, and the draft ANSI standard in 1982. Kurtz wrote in 1984 that "if there are no GOTO or similar statements, line numbers are not needed" ([Creative Computing](https://atarimagazines.com/creative/v10n11/226_Basic_is_back.php)). True BASIC is the Kemeny and Kurtz answer, with no line numbers, built-in matrix arithmetic, global and local variables, and recursion, compiled to an intermediate code ([Wikipedia: True BASIC](https://en.wikipedia.org/wiki/True_BASIC)). It implies a text-file editor workflow that conflicts with the C64 model; a design has to pick one.

The standards are at the two extremes. ECMA-55 / ANSI X3.60-1978 Minimal BASIC requires line numbers 0 to 9999, names of one letter plus one digit, numeric arrays only, no string functions and no AND/OR/NOT ([Wikipedia: Minimal BASIC](https://en.wikipedia.org/wiki/Minimal_BASIC)). Its conformance suite is public (NBS SP 500-70, [volume 1](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nbsspecialpublication500-70v1.pdf)). The maintained conformant interpreter in the notes is bas55 (GPL v3+, [jorgicor.niobe.org/bas55](https://jorgicor.niobe.org/bas55/)). ANSI X3.113-1987 / ISO 10279:1991 Full BASIC is still in force but, as far as the notes found, no implementation covers all of it ([Wikipedia: BASIC](https://en.wikipedia.org/wiki/BASIC)); the notes did not retrieve its content and treat it as a menu. The 16-bit structured dialects share one recipe: SUB/FUNCTION with parameters, block IF, SELECT CASE, WHILE/DO loops, multi-character typed names, and optional line numbers or labels. QuickBASIC 4.0 introduced a "threaded p-code interpreter" and syntax-checks each line as it is typed ([EDM2](https://www.edm2.com/index.php/QuickBASIC)). QBasic stores code in an intermediate form and displays labels instead of line numbers ([Wikipedia: QBasic](https://en.wikipedia.org/wiki/QBasic)). AmigaBASIC, GFA BASIC and FreeBASIC's `-lang qb` mode appear in the notes only by name and one-line summary; their language details were not retrieved.

## Today's small interpreters trade license, size, and numbers

MMBasic (PicoMite) is the popular modern embedded BASIC. It is GW-BASIC-like with ANSI Full BASIC structures (SUB/FUNCTION, `DO/LOOP`, `SELECT CASE`, block IF), optional line numbers, 32-character names, **64-bit integers plus double floats**, 255-character strings, a built-in VT100 full-screen editor, and tokenization when the program is stored. The manual claims "up to 100,000 lines per second", a vendor figure; the notes found only anecdotal forum timings ([PicoMite manual](https://embdev.net/attachment/588774/PicoMite_User_Manual.pdf)). Its implementation limits are small and fixed: five array dimensions, 20 nested FORs, 320 combined GOSUB/SUB/FUNCTION levels, 256 globals (same manual). Its license is murky: the author's page says the source "may not be distributed or made available to others without specific written permission" ([mmbasic.com/source.html](https://mmbasic.com/source.html)), while the MMB4L port uses a modified 4-clause BSD license with advertising and startup-message terms ([LICENSE.MMBasic](https://raw.githubusercontent.com/thwill1000/mmb4l/main/LICENSE.MMBasic)). The notes conflict on what the PicoMite repository itself permits, so any reuse of MMBasic code needs a license check.

The small C interpreters are the readable ones. uBASIC (Adam Dunkels, BSD-3) has if/then/else, for/next, let, goto, gosub, print and expressions, with integer variables of one-letter names, no editor, and a tokenizer plus direct interpreter in a few files ([GitHub](https://github.com/adamdunkels/ubasic)). TinyBasicPlus (MIT) runs in about 1100 bytes of RAM on an ATmega328 ([GitHub](https://github.com/BleuLlama/TinyBasicPlus)). my_basic (MIT) claims a footprint under 128 KB with redefinable `int_t`/`real_t`, but it needs malloc and more libc ([GitHub](https://github.com/paladin-t/my_basic)). Bas (Michael Haardt, 2.4) "tokenises the source and resolves variable and jump-target references before running" ([NuttX Bas docs](https://nuttx.apache.org/docs/12.6.0/applications/interpreters/bas/index.html)). Its license wording is inconsistent (BSD in one place, MIT in another). Matrix Brandy is about 39,000 lines of GPL C and BBC BASIC for SDL is zlib-licensed, with the "BBC BASIC" name non-transferable to forks ([Debian](https://sources.debian.org/src/brandy/1.23.6-1/READ.ME), [GitHub](https://github.com/rtrussell/BBCSDL)). EhBASIC is "free but not copyright free" and restricts commercial use, so its code should not be copied into a permissively licensed ROM ([Symon README](https://git.applefritter.com/6502/symon/src/branch/master/samples/ehbasic/README.txt)). EndBASIC (Rust, AGPL v3+) takes inspiration from Locomotive BASIC and QuickBASIC and has a built-in editor and REPL ([GitHub](https://github.com/endbasic/endbasic)). yabasic (MIT) and SmallBASIC (GPL) are still maintained.

The Tiny BASIC tradition is the size floor and the main alternative implementation technique. The 1975 Design Note specified 16-bit integers, 26 variables A-Z, no strings or arrays, and an IL virtual machine of 32 commands so a port rewrites only the IL interpreter; the original IL is 346 bytes. Listed sizes run from 1.77 KB for Palo Alto Tiny BASIC (a direct interpreter) to 4 KB for NIBL, against a 2-3 KB goal ([Wikipedia: Tiny BASIC](https://en.wikipedia.org/wiki/Tiny_BASIC); [Hackaday](https://hackaday.io/project/204482-cpu-running-basic)). The notes found only a few BASICs on soft cores (Tiny BASIC on a CDP1802 FPGA core and in the Gigatron ROM) and none for similar word-addressed 32-bit CPUs; absence in search results is not proof of absence.

Numbers without an FPU are thinly sourced. The one measured data set is Thumb-1 soft float on Cortex-M0: add about 116 bytes plus a 178-byte shared helper at 31-76 cycles, multiply about 112 bytes at 73-97 cycles, and float printf costing about 9.6 kB of flash against 2.8 kB for a compact `ftoa()` ([GCC patch v4](https://inbox.sourceware.org/gcc-patches/cover.1610363037.git.gnu@danielengel.com/T), [FloatToAscii](https://github.com/koendv/FloatToAscii/blob/main/extras/doc/speed_comparison.md)). These are for a different instruction set and hand-written assembly, not for C compiled to NICE. The notes found no 16.16 fixed-point BASIC and no cycle counts for rv32 or wasm soft float.

## Design options and trade-offs for the NICE ROM (inference, not sourced fact)

Everything in this section is the report writer's reasoning from the findings above. None of it was tested on the target.

**Numbers.** The sources point to an integer-first design. The BBC and Apple Integer results show that the fast path dominates benchmarks, and Atari shows the opposite lesson: never route line numbers or array indexes through the number format. With 32-bit words and a hardware multiplier and divider, three options exist. The first is signed 32-bit integers only (Tiny BASIC and uBASIC style, plus BBC `%`); it is the smallest and fastest, and it loses SQR, SIN, LOG and decimal fractions, which games and demos use. The second is a 16.16 fixed-point type beside integers; it needs only the 32x32 multiply with 64-bit product and the divider, makes printing trivial compared with float conversion, and gives usable trigonometry through a table, at the cost of range (about +/-32768) and a second type's worth of rules. The third is a software single-precision float beside integers (BBC and Microsoft shape); it matches what V2 and BASIC 65 users expect and covers the C library's soft-float if the code is written in C, but it costs roughly kilobytes of ROM and slower arithmetic. The Cortex-M0 figures suggest 1.5-3 KB for add, multiply, divide and conversions, but that is an extrapolation. A hybrid of integers by default with one decimal-capable type, selected by suffix as in BASIC 65 and BBC, keeps the common loop fast. The decision that most affects the other choices is whether `PRINT 1/3` should print 0, 0.3333, or 0.33333334.

**Strings.** The C64 collector's behavior is the cautionary case. With 64K words of RAM, a length-prefixed string with a back pointer (the 3.5/4.0/7.0 fix) or a copying compactor is cheap, and fixed-capacity strings (Atari, Sinclair) avoid collection entirely. Word addressing makes the character representation the real question, and no source covers it. One character per word wastes memory but makes LEFT$, MID$ and indexing trivial. Four packed characters per word saves RAM but needs shift-and-mask code in every string operation, and string slicing then needs byte-offset arithmetic. For an 80x25 screen where each cell is already a word, one character per word is the likeliest fit, but the notes cannot confirm what the screen memory holds, which is for the reader to check.

**Program storage and speed.** The three storage styles are Microsoft (token plus text), Atari (full pre-parse with names as indexes), and BBC/Sinclair (tokens with binary extras). On a word-addressed machine one token or operand per word is natural, and 32-bit words make Atari-style constants nearly free compared with 6502 bytes. The Atari approach gives syntax errors at entry and needs a lister that regenerates text and loses the user's spacing; Bas resolves jump targets before running, which is the same idea with less machinery. The speed fixes that Turbo-BASIC XL proved are independent of the encoding: resolve or cache GOTO/GOSUB targets, store the loop-body address in each FOR frame, and keep a fast integer path. A line-number index (rebuilt on each edit, or filled on first use) removes the linear scan. A pre-parsed postfix form turns evaluation into a simple stack machine; a precedence-climbing evaluator over tokens (the Microsoft approach) needs less entry-time code and is what the C library route would produce most easily. Full p-code (QuickBASIC, True BASIC) adds a compile step and a decompiler and is probably not justified at 32K words unless speed is the primary goal, though the notes have no figures on the cost either way. Variable lookup splits the same way: Microsoft's linear search is slowest, BBC's fixed A%-Z% slots and per-letter chains are fast and tiny, Atari's name-table index is fastest but caps the count. Bucketing by first letter is the cheap middle path; resolving names to table indexes at tokenize time is better if renumbering and deletion of the name table are acceptable.

**Control structure and errors.** BBC-style `PROC`/`FN` with `LOCAL`, `REPEAT/UNTIL`, `WHILE`, and multi-line `IF...ELSE...ENDIF` give structure without floats, and BASIC 65's `BEGIN/BEND` becomes unnecessary once IF is multi-line. All the frames (FOR, GOSUB, PROC, expression temporaries) can live in one tagged region, so an error unwinds by resetting one pointer, clearing temporaries, and invalidating CONT; this is how the Microsoft source and GW-BASIC both do it. GW-BASIC's `ON ERROR`/`RESUME` state is three fields (handler line, in-handler flag, saved statement pointer), and BASIC 65's `TRAP`/`RESUME`/`ER`/`EL`/`ERR$` is an equivalent a C64 user already knows. Two-letter error codes (the msbasic `CONFIG_SMALL_ERROR` option) are a way to save ROM; the notes' estimate of about 250 bytes saved is unverified.

**Editing and screen.** The notes' strongest design argument is that the Commodore screen-scraping editor is almost free when the screen is in memory: cursor keys move over the screen, RETURN copies the logical line (from the first row of the logical line to the last non-blank character) into the input buffer, and the tokenizer stores it. The state is a "row continues" flag per row, and quote mode can be dropped with ASCII-only input. An 80x25 screen allows a 160-column or 80-column logical line, avoiding the C64's 80-character loss on edit. Delete-by-number-alone, replace-by-retyping and copy-by-renumbering all fall out of one "find, delete, insert if non-empty" routine, which also covers CONT invalidation. The alternatives are a buffer-based editor with checking at entry (Sinclair, Atari, QBasic), which gives early errors but needs the parser at entry time, or a full-screen text-file editor (MMBasic, True BASIC, QBasic), which needs an editor and a source store. For a ROM at 32K words, the BASIC 65 command subset AUTO, RENUMBER, DELETE and LIST ranges, plus FIND/CHANGE with its tokenized-versus-literal delimiter trick, is the best value for the least code.

**Implementation language.** The choice between NICE assembly and C via wasm32 is not addressed by any source. The facts that bear on it: the readable references are small C programs (uBASIC, TinyBasicPlus) and heavily commented assembly (Microsoft 6502 source, BBC Z80 source), the Tiny BASIC IL approach makes an assembly interpreter small but slow, and the licensing notes above limit what code can be copied. The practical split is to write the evaluator, tokenizer and string handling in C from a design like uBASIC or the Microsoft source, and keep screen and keyboard glue in assembly, with the size of the compiled C the main unknown.

## Conclusion

The survey changes the question from "which dialect" to "which handful of mechanisms". Language surface (hundreds of keywords in BASIC 65, a dozen in Tiny BASIC) matters little to speed and size. The measured differences, 6502 BBC against Atari BASIC by a factor of about 3 to 4 at the same clock class, come from the line search, the FOR frame, the number format, and the string collector, and all four are well understood and cheap on a 32-bit word machine. The interpreter-internal evidence is stronger than the evidence about users: popularity and sales figures were not sourced, so "most popular" is ranked here by influence and survival, not by counts.

The weakest areas are exactly those the target depends on: the cost of soft float in C on a NICE-like CPU, the BASIC 65 ROM size and its use of the hardware multiplier, and the syntax and semantics of the structured dialects other than BBC BASIC and Dartmouth. A small prototype of the integer evaluator and of the screen-line editor in C would settle more of the open trade-offs than further reading.

## Facts the notes left unverified

The notes marked these as memory or not found, and this report does not rely on them: BASIC 65's float format (inferred from 5-byte items, not stated) and whether it uses the hardware multiplier; BASIC 65 and GW-BASIC ROM or executable sizes; per-version keyword counts and ROM sizes for Commodore BASIC 3.5/7.0 (C64 BASIC at 8 KB and Applesoft at about 10 KB are memory); GW-BASIC's `!`/`#` suffixes and ON KEY/ON TIMER; EDIT in BASIC 65 (no entry in the reference); BBC BASIC syntax details (`?`, `!`, `$` indirection, `ON ERROR`, copy cursor ownership, 6502 float mantissa split, GOTO search strategy and FOR frame size) and BBC's 5-byte format layout (nearest source is the BB4W description); the exact KERNAL screen-editor mechanism; Atari TRAP details and Atari expression-to-postfix conversion; ECMA-55 numeric limits (the "6 digits, 18-character strings, 15-column zones" values are memory); ANSI Full BASIC content; GFA, AmigaBASIC, PowerBASIC, Visual Basic and Liberty BASIC language details; QuickBASIC p-code format and BASCOM speedups; MMBasic's exact license, firmware size, GOTO lookup method and the clock behind its 100,000 lines per second claim; source sizes and numeric types for yabasic, SmallBASIC and Chipmunk Basic; the identity of "nanoBASIC"; popularity and sales numbers for any machine; and any cycle count for soft float on rv32 or wasm. The Dartmouth "14 statements" figure sometimes quoted is not supported by the source read, which lists 12.
